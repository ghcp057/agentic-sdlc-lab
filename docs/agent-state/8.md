# Issue 8: Order status history

## Scope

Add `GET /orders/{id}/history` to return the order's complete status history,
including the status and the timestamp at which each entry was recorded.

The implementation adds an order-status-history model/table, an Alembic
migration, repository and service support, a response schema and authenticated
route, and unit and integration coverage. History is recorded for the initial
`RECEIVED` status and for every later status transition. The endpoint must
preserve the existing order ownership check and return entries in chronological
order.

The shared interface is exactly:

```text
OrderRepository.add_history(order_id, status)
```

Use the existing order repository/database session so history records are
written in the same transaction as the corresponding order status change.

## Risks

Every current place that assigns or persists an order status must be covered;
logging only the status changes initiated from the orders route would omit
payment-driven transitions:

- `app/modules/orders/models.py` — `Order.status` defaults to `RECEIVED`.
  Initial order creation must create the initial history entry as part of the
  same database transaction.
- `app/modules/orders/repository.py` — `OrderRepository.update_order` can
  assign any supplied field, including `status`; `create_order` and `save`
  persist order objects. Preserve history if these repository methods are
  called directly, not just through the current service path.
- `app/modules/orders/service.py` — `update_order` applies a requested status
  through `setattr`; `cancel_order` directly assigns `CANCELLED`. These are
  distinct service mutation paths.
- `app/modules/orders/routes.py` — `PUT /orders/{id}` reaches
  `service.update_order`; `POST /orders/{id}/cancel` reaches
  `service.cancel_order_with_invoice` and then `cancel_order`. Keep existing
  authentication, ownership, and error behavior.
- `app/modules/payment/service.py` — `generate_invoice` advances an order to
  `PROCESSING` through `order_service.update_order`. This payment flow must
  produce history as well.
- `app/modules/payment/repository.py` —
  `mark_invoice_paid_and_update_order` directly assigns the supplied order
  status (`FULFILLED` for both payment-by-invoice-ID and payment-by-order-ID
  flows); `refund_invoice_and_cancel_order` directly assigns `CANCELLED`.
  Record both transitions atomically with the invoice and order changes. These
  methods share the SQLAlchemy session with the orders repository.

Additional risks and checks:

- A history row must not be committed if its corresponding order change rolls
  back, or vice versa. Payment updates already combine invoice and order
  changes in one transaction; preserve that atomicity.
- Status-only history should not be emitted for updates that leave the status
  unchanged or change unrelated order fields.
- Decide and test the foreign-key/deletion policy for history when the existing
  order delete operation removes an order. Do not silently lose history or
  break order deletion without documenting the selected behavior.
- Confirm timestamp semantics and ordering are consistent with the project
  database. Use a database-generated timestamp or an equivalent consistent
  UTC-aware value.
- The new table requires a database migration. A human must create/review and
  apply the migration; implementation agents must not generate or apply it.

## Ordered steps

1. Implement the status-history model and repository query/write operations.
   Define the status and timestamp fields, foreign key and deletion behavior.
   Add `OrderRepository.add_history(order_id, status)` with the exact shared
   interface above.
2. Record the initial `RECEIVED` entry when creating an order and record
   transitions in the order service paths (`update_order` and `cancel_order`).
   Ensure non-status updates do not create entries.
3. Cover payment-driven changes. Keep history writes in the same transaction
   as the order and invoice writes for invoice generation, payment completion,
   and refund/cancellation.
4. Add a history response schema and service method. Return the complete
   history in chronological order, including timestamps; define behavior for
   an unknown order using the existing order-not-found convention.
5. Add authenticated `GET /orders/{id}/history`, verify order ownership, and
   map not-found/ownership errors consistently with the existing order routes.
6. Add unit tests for initial history, each service/payment transition path,
   no-op/non-status updates, ordering, and missing orders. Add integration
   tests for endpoint authorization, response fields/order, and the intended
   order-deletion behavior.
7. Have a human create and review the Alembic migration for the history table,
   then apply it in the target database. Validate the migrated schema and run
   the focused unit and integration tests.
8. Review all status mutation points listed above against the history-writing
   implementation before closing the issue.
